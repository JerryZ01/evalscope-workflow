# EvalScope Workflow 简历与面试准备手册

本文用于帮助项目作者把 EvalScope Workflow 作为简历核心项目进行准备。内容以当前仓库实现为准，区分已经实现的能力、现阶段限制和生产化演进方案。

## 1. 项目定位

### 1.1 一句话介绍

EvalScope Workflow 是一个基于 FastAPI、React、LangGraph 和 EvalScope 的模型评测工作流平台，将命令行评测转化为可配置、可确认、可跟踪、可诊断和可展示报告的 Web 工作流。

### 1.2 30 秒版本

传统 EvalScope 使用方式更接近单次命令行任务，配置、日志、状态和报告容易分散。该项目为模型评测增加了 Web 管理界面和持久化工作流，支持模型配置、数据集和指标选择、人工确认、后台评测、SSE 进度、错误诊断、失败重试与结果报告。后端使用 FastAPI 和 SQLAlchemy，LangGraph 管理评测状态流转，真正的 EvalScope 任务在独立子进程中执行。

### 1.3 3 分钟版本

项目解决的是模型评测从“个人脚本”走向“团队公共能力”的问题。

用户先维护模型 API 配置，再选择数据集、指标、评测引擎和生成参数创建任务。启动任务后，LangGraph 依次完成配置准备和参数校验，在人工确认节点前写入 checkpoint 并暂停。用户确认后，接口返回 `202 Accepted`，评测在后台继续执行。EvalScope 被放入独立子进程，主服务负责状态持久化、日志采集、SSE 推送、取消和结果汇总。任务成功后生成分数、指标和报告；失败后按错误类型诊断，并对网络或限流类错误进行有限重试。

项目重构的重点包括：统一所有评测入口到同一工作流，统一 SQLAlchemy 数据访问，避免 API Key 进入响应和 LangGraph checkpoint，增加共享令牌认证与安全 Cookie，并为确认、重试、checkpoint 迁移和任务持久化添加自动化测试。

当前定位应表述为“功能闭环完整的内部评测平台原型”，而不是已经支持大规模生产调度的平台。

## 2. 项目价值

### 2.1 解决的问题

1. 命令行配置门槛高，非算法用户难以独立发起评测。
2. 模型、数据集、指标和生成参数缺少统一管理。
3. 长任务缺少稳定的状态、日志和进度入口。
4. 高成本评测执行前缺少人工确认边界。
5. 失败原因分散在日志中，复跑和续测成本高。
6. 结果和报告散落在输出目录，不便于团队查询与比较。
7. API Key 容易随着任务状态或调试接口泄露。

### 2.2 适用场景

- 企业内部模型选型和基线对比
- OpenAI 兼容模型服务验收
- 模型版本升级前后的回归评测
- 不同生成参数和数据集组合实验
- 模型上线前的质量检查入口
- 评测过程演示、教学和内部协作

### 2.3 不适合直接宣称的场景

- 大规模多租户生产平台
- 分布式、严格一次执行的任务系统
- 已完成企业级 RBAC 和密钥托管的平台
- 已经验证高并发和海量任务吞吐的系统
- 能完全保证评测科学性和 benchmark 无污染的系统

### 2.4 为什么形成这样的架构

一开始要解决的并不是“如何使用更多框架”，而是如何把一次 EvalScope 命令变成团队可以反复使用、可以追踪和可以控制成本的评测任务。

评测任务有几个区别于普通 CRUD 的特点：

1. 执行时间长，HTTP 请求不能一直等待。
2. 可能调用付费模型或占用 GPU，执行前需要确认参数和成本。
3. 第三方评测代码可能同步阻塞，不能直接运行在 Web event loop 中。
4. 任务可能失败、重试、取消或续测，需要明确的状态流转。
5. 模型凭据敏感，不能随着工作流状态和报告任意传播。
6. 结果不仅是数据库记录，还包括日志、原始输出和 HTML 报告。

因此架构逐步形成了以下职责分工：

- React 负责降低配置门槛和展示任务过程。
- FastAPI 负责短请求、参数校验和对外 API，不直接等待长评测。
- LangGraph 负责表达人工确认、条件分支、诊断和重试。
- 子进程负责隔离 EvalScope 的阻塞执行并提供取消边界。
- 业务数据库负责可查询任务状态，checkpoint 负责工作流节点恢复。
- SSE 负责实时体验，状态 API 负责断线后的事实查询。

这套架构不是从第一天一次设计完成的，而是随着执行入口重复、状态不一致、确认接口阻塞、秘密进入持久化状态和启动误报等问题逐步收敛出来的。

### 2.5 架构演进与困难

#### 阶段一：把 EvalScope 包装成 Web 任务

最初目标是让用户通过页面配置和启动 EvalScope。这个阶段解决了可用性，但执行逻辑仍接近脚本封装，多个入口可能各自维护状态。

#### 阶段二：引入显式工作流和人工确认

评测具有费用和资源风险，因此增加配置摘要与人工确认。LangGraph 用于表达暂停、恢复、成功、失败和重试路径。

遇到的问题是自动重试可能再次经过确认边界。解决方式是增加一次性的 `await_confirmation` 节点，让重试环只在 `run_eval`、诊断和递增重试节点之间运行。

#### 阶段三：统一执行入口和数据访问

不同 API、工作流和旧 runner 曾存在各自推进任务、直接写固定 SQLite 的情况。这会导致同一个任务在不同路径下产生不同状态。

解决方式是让兼容入口委托统一工作流，并抽取 `task_state.py`，由配置化 SQLAlchemy session factory 统一维护状态、进度、时间、日志和输出路径。

#### 阶段四：补齐异步语义和秘密边界

确认接口如果等待完整评测，会导致请求超时；如果把 API Key 放入 `EvalState`，又会被 checkpoint 持久化。

解决方式是确认接口返回 `202 Accepted`，使用后台任务恢复图；工作流只保存 `has_model_key`，真正执行时按任务 ID 即时读取凭据，同时清理旧 checkpoint 中的历史敏感状态。

#### 阶段五：解决实际运行故障

开发过程中出现过前端进程存在但功能不可用、启动脚本仍报告成功的问题。根因是旧后端占用端口且处于内核不可中断状态，新 Uvicorn 实际绑定失败。

解决方式是将启动成功的判断从“进程命令已经执行”改为“后端 health、前端页面和前端代理全部返回成功”，并在端口无法释放时自动选择备用后端端口。

### 2.6 项目实际带来的价值

#### 对评测使用者

- 将模型、数据集、指标和生成参数集中到一个任务表单中，降低记忆 CLI 参数和目录结构的成本。
- 启动后可以查看确认状态、进度、日志、失败原因和报告，不需要持续守在终端。
- 失败任务可以重试或续测，已经产生的输出目录可以继续复用。
- 评测完成后保留配置和结果记录，便于回看一次分数是如何产生的。

#### 对团队

- 形成统一评测入口，减少不同成员维护不同脚本和结果格式。
- 模型配置可以复用，评测结果能够通过任务 ID 共享和追踪。
- 人工确认降低参数错误导致的大规模无效调用和费用风险。
- 标准化报告为模型选型、版本回归和上线验收提供共同交付物。

#### 对工程维护

- 工作流、业务状态和评测执行有明确职责边界，问题可以定位到 API、节点、子进程、数据库或输出目录。
- 统一数据访问后可以替换数据库并增加事务控制，不需要逐个修改执行路径。
- 秘密不再进入 API 响应和新 checkpoint，降低调试、备份和状态查看造成的暴露面。

### 2.7 可以诚实使用的当前成果

以下内容可以从当前系统直接验证，但它们属于“能力范围”，不等同于线上业务收益：

| 成果 | 当前可验证值 | 代表的价值 |
|------|--------------|------------|
| 数据集目录覆盖 | 约 158 个 EvalScope 数据集元数据 | 用户不需要手工查找和拼写大部分数据集配置 |
| 评测生命周期 | 创建、校验、确认、执行、诊断/重试、结果/报告闭环 | 从单次命令提升为可跟踪任务 |
| 自动错误处理 | 对连接、超时、限流等错误进行分类并最多自动重试 1 次 | 减少部分临时故障下的人工重跑 |
| 凭据传播控制 | API 响应和新 LangGraph checkpoint 中密钥明文为 0 | 缩小密钥泄漏面 |
| 关键行为回归 | 8 个后端测试覆盖确认、重试、持久化和安全边界 | 降低核心流程修改后的回归风险 |

不能把“158 个数据集”直接说成“支持 158 种业务场景”，也不能把自动重试 1 次描述成完整容灾。

### 2.8 应该补测的业务量化指标

要把项目真正写成有业务成果的简历项目，建议进行一轮 CLI 与平台对照实验。选择同一名操作者、同一模型和 10 至 20 个相同小样本任务，记录以下指标：

| 指标 | 定义 | 数据来源 | 建议目标，不是当前成果 |
|------|------|----------|------------------------|
| 任务准备时长 | 从收到评测需求到任务成功启动的时间 | 人工计时、任务 created/started 时间 | 相比 CLI 降低 50% 以上 |
| 配置错误率 | 因参数、路径、模型类型错误而无法启动的任务占比 | 失败分类、对照实验记录 | 降低到 5% 以下 |
| 无人值守完成率 | 确认后无需人工处理即可结束的任务占比 | 任务事件和状态 | 达到 90% 以上 |
| 报告交付时延 | 评测完成到报告可查看的时间 | completed_at、报告可访问时间 | 小于 1 分钟 |
| 失败定位时间 MTTR | 从失败发生到确认根因所需时间 | 故障演练计时 | 相比查原始日志降低 50% 以上 |
| 配置复用率 | 使用已管理模型或历史配置创建的任务占比 | 模型与任务关联记录 | 持续提升 |
| 可追溯率 | 能关联配置、日志、结果、报告和代码版本的任务占比 | 任务审计 | 目标 100% |
| 无效调用成本 | 因配置错误产生的 Token 或 GPU 浪费 | 模型账单、资源监控 | 相比无确认流程显著降低 |

计算示例：

```text
任务准备效率提升 = (CLI 中位准备时长 - 平台中位准备时长) / CLI 中位准备时长

无人值守完成率 = 确认后无人工干预完成的任务数 / 已确认任务总数

可追溯率 = 同时具备配置、日志、结果和报告的任务数 / 已完成任务总数

配置错误率 = 配置类失败任务数 / 启动任务总数
```

在完成对照实验前，简历上应写“建立了可量化的任务闭环”，不要写“效率提升 70%”。实验完成后再把真实中位数、样本量和测试环境写入简历。

### 4.1 前端

- React、TypeScript、Vite、Ant Design
- Axios 统一 API 客户端，响应拦截器处理业务错误和 `401`
- `AuthGate` 检查认证状态并展示共享令牌登录页
- TaskDetail 通过 SSE 接收运行事件，同时轮询工作流确认状态
- Vite 将 `/api` 和 `/health` 代理到可配置后端地址

### 4.2 后端

- FastAPI 提供任务、目录、模型、工作流、结果、认证和 AI 助手 API
- SQLAlchemy AsyncSession 管理业务数据库访问
- LangGraph StateGraph 编排评测生命周期
- `multiprocessing.Process` 隔离 EvalScope 的阻塞和高资源执行
- SSEManager 向在线前端广播进度和日志事件

### 4.3 存储

- 业务数据库保存任务、模型配置、目录缓存和业务状态
- LangGraph checkpoint 数据库保存工作流执行上下文
- 输出目录保存 EvalScope 日志、原始结果和 HTML 报告
- 三类存储目前不是同一个原子事务，需要通过状态校验和恢复机制进一步保证一致性

## 6. 核心执行链路

### 6.1 创建任务

1. 前端提交模型、数据集、引擎和生成参数。
2. `POST /api/tasks` 创建 `EvaluationTask`。
3. 初始状态为 `pending`，配置保存在业务数据库。
4. API 响应只返回 `has_model_key`，不返回密钥内容。

### 6.2 启动并等待确认

1. 前端调用 `POST /api/workflow/{task_id}/start`。
2. API 从数据库构建不包含 API Key 的 `EvalState`。
3. 清理该任务旧 checkpoint，避免历史执行上下文污染新运行。
4. LangGraph 执行 `prepare_config` 和 `validate_params`。
5. 图在 `await_confirmation` 节点前中断。
6. 前端查询状态后派生出 `confirming` UI 状态。

### 6.3 确认并执行

1. 前端调用 `POST /api/workflow/{task_id}/confirm`。
2. 后端确认图确实停在 `await_confirmation`。
3. 可选修改仅允许生成参数、数据集参数、样本限制和批大小。
4. 使用 `asyncio.create_task` 继续工作流并立即返回 `202`。
5. `run_eval` 在真正执行前按任务 ID 即时读取 API Key。
6. EvalScope 在子进程中运行，主进程持续读取日志并发送 SSE。
7. 成功进入 `collect_results`，失败进入 `diagnose_error`。

### 6.4 失败重试

1. `_classify_error` 将错误归类为认证、连接、限流、沙箱、资源或数据问题。
2. `should_retry` 只对网络、超时、限流和部分服务错误重试。
3. 当前最大自动重试次数为 1。
4. 重试复用工作目录，避免重新完成已经缓存的评测工作。
5. `await_confirmation` 位于重试环之外，因此自动重试不会再次要求人工确认。

### 6.5 取消

1. 取消内存中的后台协程。
2. 向已登记的 EvalScope 子进程发送 `SIGTERM`。
3. 进程超时未退出时执行强制终止。
4. 将业务任务状态更新为 `cancelled`。

## 7. 状态设计

### 7.1 业务状态

```text
pending -> running -> completed
   |          |
   |          +----> failed
   |          +----> cancelled
   +---------------> cancelled
```

数据库没有独立的 `confirming` 状态。前端根据以下条件派生：

```text
task.status == pending
and workflow.waiting_for_confirmation == true
=> effectiveStatus == confirming
```

### 7.2 为什么业务状态与工作流状态分开

- 业务状态适合列表查询、筛选、统计和用户展示。
- 工作流状态包含节点位置、重试计数、诊断和配置摘要。
- 如果把完整工作流状态全部放入业务表，字段会快速膨胀且恢复语义不清晰。
- 如果只保留 checkpoint，普通业务查询会依赖 LangGraph 内部结构。

### 7.3 当前一致性边界

- 业务数据库提交和 checkpoint 写入不是分布式事务。
- 输出文件写入也不属于数据库事务。
- 服务异常时可能出现 DB 显示 `running`，但内存任务已经不存在。
- 生产化需要启动扫描、租约、幂等状态转换和结果对账。

## 8. 关键技术决策

### 8.1 为什么选择 FastAPI

- 原生支持异步 API 和类型化请求模型。
- OpenAPI 文档生成方便平台联调。
- 与 Python 评测生态集成成本低。
- 需要注意：异步框架不会自动让 CPU 或阻塞任务变成非阻塞任务。

### 8.2 为什么选择 LangGraph

- 评测过程存在条件路由、人工确认、checkpoint 和重试回路。
- 节点和边比嵌套业务函数更容易展示状态机语义。
- LangGraph 不是任务队列，不能替代跨进程 worker 和可靠消息投递。
- 如果流程永远只有顺序执行，普通服务层状态机可能更简单。

### 8.3 为什么使用子进程执行 EvalScope

- EvalScope 可能包含同步、CPU/GPU 密集和第三方库代码。
- 子进程避免长评测直接阻塞 FastAPI event loop。
- 子进程提供较明确的取消和资源隔离边界。
- 当前进程注册表仍是内存结构，服务重启后无法继续管理旧子进程。

### 8.4 为什么确认接口返回 202

- HTTP 请求只负责接受执行意图，而不是等待评测完成。
- 长连接容易受到代理超时、客户端断开和资源占用影响。
- `202` 表示请求已接受，但结果需要通过任务状态或事件通道继续查询。

### 8.5 为什么统一 SQLAlchemy 数据访问

- 避免工作流和旧 runner 使用固定 SQLite 路径直接写库。
- 保证所有运行路径遵守同一数据库配置。
- 统一事务、时间字段、状态规范化和测试替换点。
- 为未来迁移 PostgreSQL 提供稳定边界。

### 8.6 为什么 API Key 不进入 checkpoint

- checkpoint 是持久化状态，可能长期留存、备份或被调试读取。
- 状态只保存 `has_model_key`，执行节点按任务 ID 即时读取凭据。
- schema 版本变化时会清理旧 checkpoint、截断 WAL 并执行 `VACUUM`。
- 该迁移策略优先移除历史秘密，但会牺牲旧工作流恢复能力。

### 8.7 为什么 SSE 与轮询同时存在

- SSE 适合服务器主动推送运行进度和日志。
- 人工确认状态来自 checkpoint 查询，当前前端通过轮询获取。
- SSE 断线后仍可通过数据库状态恢复页面展示。
- 生产环境应增加事件 ID、断线续传和跨实例消息总线。

## 9. 安全设计与边界

### 9.1 已实现

- 可选共享 Token 保护 `/api/*` 路径。
- 登录成功后设置 HttpOnly、SameSite=Strict Cookie。
- Token 比较使用 `secrets.compare_digest`。
- Cookie 中保存共享 Token 的单向摘要，不保存明文 Token。
- API 响应使用 `has_api_key` 或 `has_model_key`，不序列化密钥。
- LangGraph 状态不保存模型 API Key。
- checkpoint security schema 迁移清理历史敏感状态。
- CORS、Cookie Secure 和会话有效期可配置。

### 9.2 当前限制

- API Key 当前仍以明文列存储在业务数据库。
- 共享 Token 不能区分用户，无法实现 RBAC 和操作审计。
- Cookie 摘要由共享 Token 确定，不是服务端随机会话 ID。
- 默认 `SESSION_COOKIE_SECURE=False` 仅适合本地 HTTP 开发。
- 默认 CORS 为 `*`，生产环境必须收紧。
- 缺少限流、CSRF 专项策略、密钥轮换和外部 Secret Manager。

### 9.3 生产化方案

- 使用 KMS 或 Vault 管理密钥，数据库只保存密文或引用。
- 引入正式身份系统、短期会话、RBAC 和审计日志。
- 强制 HTTPS、Secure Cookie 和受控 CORS 白名单。
- 对登录、模型测试和任务启动接口增加限流。
- 对报告路径、数据集参数和文件上传执行严格校验。

## 11. 当前已知问题和改进方向

| 问题 | 原因 | 推荐方案 |
|------|------|----------|
| 进程重启后后台任务丢失 | `asyncio.Task` 和进程注册表只在内存中 | 持久化队列、worker 租约、启动恢复扫描 |
| 多实例无法共享 SSE | SSE 连接保存在单进程内存 | Redis Pub/Sub 或消息总线 |
| 重复执行风险 | 缺少数据库级 claim 和版本控制 | 条件更新、行锁、幂等键、执行租约 |
| SQLite 写并发有限 | 单文件数据库锁模型 | PostgreSQL + 连接池 + Alembic |
| API Key 静态存储风险 | 业务表保存明文凭据 | KMS/Vault 或应用层 envelope encryption |
| 报告接口契约不统一 | 同一路径既被当作 HTML 又被当作 JSON | 分离 `/report` 与 `/report/meta` |
| 错误诊断较粗糙 | 基于字符串关键词分类 | 结构化异常、错误码和供应商响应映射 |
| 重试策略简单 | 固定最大一次且无退避 | 指数退避、抖动、Retry-After、预算限制 |
| 日志可能持续膨胀 | 数据库 Text 与文件同时积累 | 分片、对象存储、保留策略和日志索引 |
| 配置版本不足 | 任务只保存当时字段 | 配置快照、模型版本、数据集版本和代码版本 |

### 12.6 STAR 故事模板

#### 故事一：统一工作流与数据访问

- Situation：多个入口和执行器分别推进任务，部分路径直接写固定 SQLite 文件，存在状态不一致风险。
- Task：在保留兼容 API 的前提下，统一执行语义和持久化边界。
- Action：让旧入口委托统一工作流，抽取 `task_state.py`，通过配置的 AsyncSession 更新状态，并增加真实 SQLite 测试。
- Result：所有入口共享同一状态机，数据库路径可配置，关键状态更新能够被隔离测试。

#### 故事二：消除 checkpoint 中的秘密

- Situation：工作流状态具有长期持久化和调试读取能力，直接携带 API Key 会扩大泄漏面。
- Task：在不影响评测执行的情况下移除 checkpoint 中的密钥。
- Action：状态只保存 `has_model_key`，执行节点按任务 ID 即时读取凭据；响应 schema 脱敏；通过安全 schema 版本清理旧 checkpoint、WAL 和空闲页。
- Result：新 checkpoint 不再需要秘密，历史敏感状态得到迁移清理，并有自动化测试覆盖。

#### 故事三：启动成功误报排查

- Situation：前端进程存在但页面功能不可用，旧脚本仍打印启动成功。
- Task：判断问题在前端、代理还是后端，并让脚本能够自行发现同类问题。
- Action：分别检查监听端口、前端 HTTP、后端 health 和代理 health；发现旧后端处于内核 `D` 状态且无法释放 `5900`；脚本增加端口复查、备用端口、动态代理和健康检查。
- Result：脚本能绕开不可释放端口，只有前后端和代理均通过检查时才报告成功。

## 14. 面试 QA

### 14.1 业务与产品

#### Q1：为什么要做这个项目，直接使用 EvalScope CLI 不够吗？

CLI 适合算法工程师进行单次实验，但团队使用还需要配置复用、权限边界、任务状态、人工确认、进度日志、失败诊断和结果沉淀。项目的价值是把评测能力从个人命令升级为可共享的工作流，而不是替代 EvalScope 的核心评测算法。

#### Q2：这个项目最核心的用户是谁？

主要用户是需要反复进行模型选型、版本回归和上线验收的算法、平台和测试人员。非算法角色可以通过页面发起标准任务，算法人员仍可查看详细参数和日志。

#### Q3：项目的核心指标是什么？

现阶段更关注任务成功率、从创建到结果的完成时间、失败可诊断率、重复执行率和结果可复现率。生产化后还应统计队列等待时间、模型调用成本、worker 利用率和 SSE 连接稳定性。

#### Q4：这个项目与普通后台管理系统有什么不同？

核心区别是它管理长时间、有外部依赖、可能消耗 GPU 或 API 费用且需要人工确认的评测工作流。难点不在 CRUD，而在异步执行、状态一致性、取消、恢复、秘密管理和结果可复现。

#### Q5：项目目前达到生产可用了吗？

还没有。主流程和基础安全边界已经形成，但多实例调度、重启恢复、数据库级幂等、正式身份系统、PostgreSQL、完整 E2E 和可观测性仍需要补齐。准确定位是内部平台原型。

### 14.2 架构设计

#### Q6：请描述一次完整评测的数据流。

前端创建业务任务，启动接口从数据库构建无密钥工作流状态，LangGraph 完成配置准备和参数校验后暂停。确认接口返回 `202` 并在后台恢复工作流。执行节点即时读取凭据，启动 EvalScope 子进程，主进程采集日志并发送 SSE。成功后结果写入业务数据库并读取报告；失败后诊断并决定重试或终止。

#### Q7：为什么不把所有逻辑写在 FastAPI 路由里？

路由应处理 HTTP 协议、参数和响应，工作流负责状态转换，任务状态服务负责持久化，EvalScope wrapper 负责执行适配。分层后节点可单测，旧入口也能复用同一个启动服务，避免多套行为逐渐不一致。

#### Q8：为什么不用 Celery，反而用了 LangGraph？

两者解决的问题不同。LangGraph表达节点、分支、人工确认和 checkpoint；Celery 解决可靠投递和分布式 worker。当前原型只需要单机执行，因此先用 LangGraph 和进程内后台任务。生产化时可以让 LangGraph 负责流程语义，让 Celery、Temporal 或专用 worker 负责可靠执行。

#### Q9：为什么不直接使用 Airflow？

Airflow 更适合定时批处理和 DAG 调度，交互式人工确认、秒级 API 状态和产品内嵌体验不是它最轻量的场景。如果评测发展为大规模定时批任务，Airflow 可以成为调度选项。

#### Q10：为什么业务数据库和 checkpoint 分开？

业务数据库服务列表、权限、筛选和报表；checkpoint 服务节点恢复。二者的数据形态和访问模式不同。代价是需要处理双写不一致，不能声称分开后自然获得强一致性。

### 14.3 LangGraph 与工作流

#### Q11：工作流有哪些节点？

`prepare_config`、`validate_params`、`await_confirmation`、`run_eval`、`collect_results`、`diagnose_error`、`increment_retry` 和 `mark_failed`。条件边根据参数校验和执行结果选择成功、诊断、重试或失败路径。

#### Q12：人工确认是如何实现的？

图以 `interrupt_before=["await_confirmation"]` 编译。首次调用执行到该节点前暂停并保存 checkpoint。确认接口检查 `state.next`，然后通过 `Command(resume=True)` 恢复图。

#### Q13：为什么需要单独的空操作确认节点？

它提供稳定的一次性人工边界。确认后流程进入 `run_eval`，失败重试从 `increment_retry` 回到 `run_eval`，不会再次经过确认节点。这样自动重试不会反复打断用户。

#### Q14：为什么启动新任务前删除旧 thread checkpoint？

同一个任务 ID 重新启动时，旧 checkpoint 可能让新执行从历史节点继续。删除旧 thread 能确保新启动从初始状态开始。代价是如果用户本意是恢复旧执行，就不能调用普通 start，而应提供独立 resume 语义。

#### Q15：`confirm` 为什么使用 `202`？

确认后评测可能持续数分钟或更久。接口只接受执行请求，因此立即返回 `202`；结果通过状态 API 和 SSE 获取。若同步等待，会受到反向代理超时、客户端断开和连接资源限制。

#### Q16：重复点击确认会发生什么？

当前先检查 checkpoint 是否在确认节点，再检查 `_workflow_tasks` 中是否已有未完成任务，后者返回 `409`。但这是进程内保护，多实例下仍不够。生产方案是数据库条件更新或租约，例如仅允许 `pending + version=n` 原子转换为 `running + version=n+1`。

#### Q17：服务在返回 202 后立即崩溃怎么办？

当前 `asyncio.create_task` 会丢失，数据库可能停留在 `running`。生产方案是把待执行意图持久化到任务队列，worker 领取时写入租约；服务启动时扫描过期租约和异常运行状态，根据 checkpoint 恢复或标记失败。

#### Q18：工作流能做到 exactly-once 吗？

当前不能。分布式系统通常也更现实地实现 at-least-once 投递加幂等处理。模型调用本身可能不可回滚，因此应使用执行 attempt、幂等键、输出目录隔离和结果去重，明确哪些节点允许重复执行。

### 14.4 异步、子进程与并发

#### Q19：FastAPI 是异步的，为什么还需要子进程？

`async` 只在等待可让出控制权的 I/O 时有效。EvalScope 及其依赖可能同步阻塞、执行 CPU/GPU 工作或维护全局缓存。放入子进程可以避免阻塞 event loop，并形成取消与资源回收边界。

#### Q20：为什么不用线程池？

线程共享解释器和进程全局状态，CPU 密集任务还受 GIL 影响，第三方库异常也更容易影响主服务。子进程隔离更强，但启动和通信成本更高。

#### Q21：子进程结果如何传回？

当前使用 `multiprocessing.Queue` 传递序列化后的报告、错误和捕获日志。主进程负责数据库写入，避免子进程绕过统一的数据访问层。

#### Q22：如何取消任务？

主进程维护 `task_id -> Process` 注册表，先发送 `SIGTERM` 并等待，超时后强制终止。工作流后台协程也会被取消。生产环境还需要处理子孙进程、GPU 资源释放和服务崩溃后的孤儿进程。

#### Q23：多 worker 部署会有什么问题？

确认请求、取消请求和 SSE 连接可能落到不同 worker，而后台任务和进程注册表只存在于发起 worker。需要共享队列、持久化执行者信息、跨实例事件总线和负载均衡策略，不能直接横向扩容当前实现。

#### Q24：如何限制并发和费用？

当前尚未形成完整配额系统。可以按模型供应商、用户和 worker 设置 semaphore 或队列并发数，增加单任务样本上限、Token 预算、超时、每日额度和熔断策略。

### 14.5 数据库与一致性

#### Q25：为什么使用 SQLAlchemy AsyncSession？

它与 FastAPI 异步请求模型匹配，提供统一模型、事务和数据库替换边界。真正的价值不是“异步更快”，而是避免同步数据库 I/O 阻塞请求，并让工作流和 API 使用同一会话工厂。

#### Q26：SQLite 有什么限制？

SQLite 部署简单，适合单机原型和测试，但写并发、锁竞争、迁移管理和多实例共享能力有限。生产环境应迁移 PostgreSQL，并为关键状态转换使用事务、条件更新或行锁。

#### Q27：如何避免两个请求同时启动一个任务？

当前仅靠状态检查存在检查后再执行的竞态。推荐使用单条条件更新：`UPDATE ... SET status='running' WHERE id=? AND status='pending'`，再检查受影响行数；也可以结合版本号和租约。

#### Q28：数据库成功但 checkpoint 失败怎么办？

当前无法通过单一事务原子提交。应定义状态机的事实来源，记录执行 attempt 和阶段，失败时通过 outbox 或恢复扫描进行补偿，而不是假设两边永远一致。

#### Q29：为什么集中实现 `task_state.py`？

它统一状态规范化、进度边界、开始完成时间、耗时和日志追加，消除固定 SQLite 路径写入。测试可替换 session factory，数据库迁移也不需要修改每个工作流节点。

#### Q30：日志直接追加到 Text 字段有什么问题？

长任务会造成大行更新、锁持有、数据库膨胀和查询变慢。生产方案是日志文件或对象存储作为主体，数据库只保存索引、摘要和游标。

### 14.6 安全

#### Q31：API Key 是否已经安全存储？

不能这样宣称。目前已经避免在 API 响应和 checkpoint 中暴露，但业务数据库仍保存明文字段。完整方案需要 KMS/Vault、加密存储、访问审计和轮换。

#### Q32：为什么只在执行节点读取 API Key？

工作流状态会持久化和被调试，携带密钥会扩大泄漏面。按任务 ID 即时读取可以让大多数节点只处理“是否存在密钥”这一事实。

#### Q33：共享 Token 认证有什么优缺点？

优点是实现简单，适合内部单团队和开发环境；缺点是无法识别用户、授权和审计，Token 泄露后影响所有人。它是基础访问边界，不是企业身份系统。

#### Q34：为什么使用 HttpOnly 和 SameSite=Strict？

HttpOnly 降低脚本直接读取 Cookie 的风险，SameSite=Strict 限制跨站携带 Cookie。生产环境还需要 HTTPS 和 Secure Cookie，并分析具体跨域部署下的 CSRF 风险。

#### Q35：checkpoint 清理迁移为什么还要 checkpoint WAL 和 VACUUM？

SQLite 删除记录不代表旧字节立即从数据库文件、WAL 或空闲页消失。截断 WAL 和 `VACUUM` 能更彻底移除历史敏感数据。代价是迁移期间有额外 I/O，并删除旧流程恢复点。

### 14.7 前端与通信

#### Q36：为什么使用 SSE，不用 WebSocket？

当前数据主要是服务端向浏览器单向发送进度和日志，SSE 基于 HTTP、实现简单且浏览器原生支持。若需要双向控制、高频二进制数据或复杂会话，再考虑 WebSocket。

#### Q37：SSE 断开后怎么办？

浏览器 EventSource 可以自动重连，页面也能重新查询数据库状态。但当前缺少事件 ID 和完整 replay，断线期间的增量日志可能丢失。可通过 `Last-Event-ID`、持久化事件表或日志游标完善。

#### Q38：为什么前端还有轮询？

当前 SSE 主要服务运行日志和进度，工作流确认位置通过 status API 查询。轮询是简单可靠的补充，但会产生额外请求。后续可以把工作流状态变化也统一为事件。

#### Q39：前端如何处理认证过期？

Axios 响应拦截器捕获 `401`，派发全局事件；`AuthGate` 收到事件后回到登录状态。该方式轻量，但大型应用更适合集中认证 store 和路由保护。

#### Q40：报告页面为什么出现 HTML/JSON 解析错误？

当前同一报告地址既被 iframe 当作 HTML 加载，也曾被前端逻辑按 JSON 读取，接口契约不清晰。应拆分报告元数据 JSON API 和 HTML 内容 API，并分别测试 `Content-Type`。

### 14.8 测试与质量

#### Q41：为什么目前只有 8 个测试也有价值？

数量不是重点，这些测试覆盖的是安全泄漏、真实 SQLite 迁移、一次性确认、重试路径、异步 `202` 和统一数据库访问等高风险行为。但它们不能替代完整 API 和浏览器 E2E。

#### Q42：如何测试 202 确实立即返回？

测试使用不会完成的假工作流，通过超时约束调用确认接口。如果接口等待后台执行，测试会超时；正确实现应立即返回并在任务注册表中留下运行中的后台任务。

#### Q43：如何测试工作流重试不会再次确认？

用内存 checkpointer 和可控的 `run_eval` 替身，让第一次返回可重试错误、第二次成功。首次恢复确认后，断言调用次数为 2 且流程最终完成，不再次停在确认节点。

#### Q44：最重要的下一条测试是什么？

使用 Playwright 完成“登录、创建任务、启动、确认、等待完成、查看报告”的 E2E。它能覆盖前端状态、代理、API、工作流和报告契约，是当前最大的测试缺口。

#### Q45：如何测试并发重复启动？

并发发送多个 start 或 confirm 请求，断言只有一个请求成功获得执行权，其余得到 `409`，同时验证只产生一个 attempt、一个输出目录和一个子进程。

### 14.9 大模型评测领域

#### Q46：如何保证评测可复现？

应保存模型唯一版本、API 供应商、数据集版本、subset、指标版本、生成参数、随机种子、EvalScope 版本、代码 commit 和执行环境。仅保存模型名称和平均分远远不够。

#### Q47：平均分高就代表模型更好吗？

不一定。需要结合任务分布、样本量、置信区间、随机波动、成本、延迟、安全要求和业务权重。不同 benchmark 的分数也不能简单相加。

#### Q48：什么是 benchmark contamination？

评测数据可能出现在模型训练语料中，导致分数高估泛化能力。应关注数据发布时间、训练截止日期、私有测试集、动态题目和污染检测，报告中说明这一风险。

#### Q49：LLM-as-a-Judge 有什么风险？

Judge 可能存在位置偏差、风格偏差、自我偏好、提示敏感和输出不稳定。应固定 Judge 版本与温度，交换候选顺序，多次采样，并使用部分人工标注校准一致性。

#### Q50：如何比较不同模型的成本收益？

同时记录准确率或任务指标、输入输出 Token、请求费用、P50/P95 延迟、失败率和吞吐，再按业务约束绘制 Pareto 前沿，而不是只按单一分数排名。

### 14.10 故障排查与部署

#### Q51：前端页面打开但数据显示不出来，怎么排查？

依次检查 Vite 是否监听、`/health` 是否能通过前端代理访问、认证 status 是否为 `200`、后端端口是否与 `VITE_BACKEND_TARGET` 一致、浏览器 Network 和后端日志。页面能打开只说明静态服务正常，不代表 API 正常。

#### Q52：为什么旧启动脚本会误报成功？

它在杀端口进程后没有确认端口释放，也没有检查 Uvicorn 是否仍存活和健康。后端绑定失败后脚本仍继续启动 Vite并打印成功。修复后脚本会检查端口、必要时选择备用端口，并验证后端、前端和代理健康状态。

#### Q53：为什么 `kill -9` 也可能无法停止进程？

Linux 进程处于不可中断睡眠 `D` 状态时，信号只能等待内核调用返回后处理。此时应先定位 `wchan` 和底层设备问题，临时绕开端口，最终重启相关内核环境或 WSL。

#### Q54：如何部署到生产环境？

前端构建为静态文件并由 Nginx 提供，后端使用受控 worker，任务由独立执行 worker 消费；数据库使用 PostgreSQL，事件使用 Redis 或消息总线，报告进入对象存储，入口启用 TLS、认证、限流和监控。

#### Q55：如何做可观测性？

当前支持可选 Langfuse 回调和普通日志。生产化应增加结构化日志、request ID、task ID、attempt ID、Prometheus 指标、分布式 trace、错误聚合和模型调用成本指标。

## 16. 建议的生产化数据模型

除现有 `evaluation_tasks` 外，可以增加：

```text
execution_attempts
  id
  task_id
  attempt_number
  worker_id
  lease_expires_at
  status
  config_snapshot
  code_version
  started_at
  completed_at
  error_code
  error_detail
  output_uri

task_events
  id
  task_id
  attempt_id
  event_type
  sequence
  payload
  created_at

credential_refs
  id
  owner_id
  provider
  secret_reference
  key_version
  created_at
  rotated_at
```

`execution_attempts` 让一次业务任务可以对应多次执行；`task_events` 支持事件重放、SSE 续传和审计；`credential_refs` 避免业务表直接保存明文凭据。
